chrome-gateways

Every way an agent, a program or you reach Chrome on these machines, each with the features it needs: agents browse without disturbing your work, every tab says who opened it, when and why, nothing is left open, and a link you click opens in the right profile. · Updated 2026-11-24 · formerly agent-chrome

1 · The context: three kinds of things open Chrome

Each one controls Chrome differently, and none can use another's way in. That is why there are three gateways.

2 · The three gateways

Agent gateway

agent-gateway/
An agent looks at a page itself: reads, clicks, fills, logs in. Mac only.
  • Claude in Chrome, in the profile of the session's Claude account
  • visible, never brought to the front
  • one window per account and desktop
  • a bar on each tab: who, when, why
  • status: working / waiting for Jean, with what to do
  • a chat with the agent in the side panel
  • logins through agent-vault, never seeing a password

Script gateway

script-gateway/
Code opens pages: scripts, tests, scheduled jobs. Mac and NAS.
  • a separate Chrome, its own data folder
  • headless: no window, ever
  • never left running
  • recorded: who, when, why
  • not flagged as a robot

Terminal links

terminal-links/
You click a link an agent printed. Agents never open windows to show you something.
  • rules for agents: always a full, clickable link
  • open-link: a claude.ai link → the profile of that terminal's Claude account
  • anything else → your own profile, or the app macOS picks
shared/ · the record ~/opt/chrome-gateways/state/: every tab of both gateways, who opened it, when, why · chrome_kit.py: the record and the Claude account profiles
agent-chrome status: what is open, who, whyagent-chrome clean + a daily checkthe bar on each tabagent-vault: which session owns a tab

One window per account and desktop: how, given macOS

macOS lets no program move a window to another desktop, and a new window always opens on the desktop you are looking at. But a tab can move freely between windows. So the extension never moves windows: it moves tabs into the window that is already there.

desktop 1
websites · Claude A
tasks · Claude A
Account A websitestasks
desktop 2 (you look here)
jobs · Claude B
Account B jobs

When a session's desktop has no window of its account and you are looking elsewhere, its tab stays where Claude in Chrome put it; the bar still names the session.

4 · Script gateway: code opening pages

Why it exists: without it, every script starts its own Chrome, which pops a window, stays running after a crash, and leaves no trace.

Never a window on your screenA script that starts a normal Chrome pops a window and takes the focus. The hook refuses an agent's shell command that starts a visible Chrome; the launcher is the allowed way.
Nothing left runningA job killed by a timeout used to leave Chrome running. A small watcher process closes Chrome as soon as the script dies.
Recorded: who, when, whyEach run is written to the same record as agent tabs, so agent-chrome status shows it.
Not flagged as a robotA plain headless Chrome announces itself as automated (measured); the launcher's settings make it look like a normal Chrome.
QuestionAnswer
Which Chrome?a separate Chrome process, started by launch_headless.py; never your normal Chrome, never a Claude account profile (no Claude is involved)
Which profile?its own data folder (where Chrome keeps cookies and logins), chosen by the script: a temporary one for public pages, or ~/opt/<repo>/chrome/ for a tool that needs a login, which you log in to once by hand
Visibilityheadless, always; it cannot change. To "see" a page, the code takes a screenshot into a file
Windowsnone. One Chrome process per data folder: a second run on the same folder reuses the running one
Mac and NASthe same on both; on the NAS (no screen) it is the only way: Chrome for Testing, installed by install.sh
Bar, status, chatnone: there is no window to put them in, and nobody to act
agent-vaultno it types only into a visible Claude in Chrome tab on the Mac (see below for how code logs in)

How code logs in: the recommendation

Take the first option that works for the site; the tool's AGENTS.md says which one it uses. Today no tool needs any of them (no ~/opt/*/chrome/ on either machine).

OptionHowWhy this rank
1No browser login: the site's APIa token in ~/.config/<tool>/secrets.env (readable by you only), read by the code; no Chrome at allnothing to expire on a page, no bot check, no password anywhere; works on the NAS
2A session kept in the tool's own data folderyou log in once, by hand, in a visible window on ~/opt/<tool>/chrome/ (two-factor included); every run then reuses those cookies, headless. When the session ends, the script sees the login form, stops with "logged out" and files a task for you to log in againno password stored at all, only a session; you stay the only one who types it
3The code types the passwordfrom the tool's own ~/.config/<tool>/secrets.env, ideally for an account made for that tool, never printed or loggedonly for a site whose session ends every day: the password then sits in a file on disk
neveran agent reading or typing a password; a password saved in the data folder's Chrome; your real accounts (LinkedIn, Facebook, WhatsApp Web) through the script gateway: a headless second login there risks a ban, so they go through the agent gateway

Option 2 needs a way for you to open that data folder in a window once. proposed launch_headless.py --login --data-dir ~/opt/<tool>/chrome --url <login page>: a visible window on that folder for you, recorded like any tab, refused inside a Claude session (so only you run it).

5 · Terminal links: you clicking

Why it exists: agents used to open windows to show you a page, on any desktop, in front of you. Now they only print a link, and you choose when to look. One case needs care: a claude.ai Artifact opens only in the Chrome profile logged in to the Claude account that made it.

an agent prints a full linkfile:///Users/jeanlescut/…, file:///Volumes/private/…, https://claude.ai/… (the rule: CLAUDE.md, "Answering the user")
→
you click it in iTerm2iTerm2 runs open-link (set by install.sh: set_iterm2_clicks.py)
→
open_link.py decidesclaude.ai link in a Claude session's terminal → that account's profile · other web link or page → your own profile · any other file → the app macOS picks

How it knows the terminal's Claude account: when a session starts, the agent gateway's hook writes its account on the tmux pane (@claude_account); open-link trusts it only while a claude process still runs there. Every click is a line in state/clicks.log. An agent cannot run open-link.
